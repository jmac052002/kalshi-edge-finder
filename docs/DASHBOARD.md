# The dashboard

`python -m kalshi_edge.dashboard` turns the reports the other commands already write into one HTML file you can open on a laptop or a phone. It makes no network request, opens the database read-only, and never trades.

```bash
python -m kalshi_edge.scan --json scan.json
python -m kalshi_edge.compare --series KXNFLGAME --json compare.json
python -m kalshi_edge.calibrate --series KXNFLGAME --json calibration.json

python -m kalshi_edge.dashboard \
  --scan scan.json \
  --compare compare.json \
  --calibration calibration.json \
  --db data/kalshi.db \
  --out dashboard.html
```

Every input is optional, as long as there is at least one. A panel with no input says which command produces it. `--compare` and `--calibration` can be repeated, one per series.

## What is on the page

| Section | Comes from | What it shows |
| --- | --- | --- |
| Freshness chips | all inputs | How old each input was when the page was built: Fresh, Stale, Not supplied, or Clock mismatch |
| Tiles | all inputs | Sides clearing costs, the median clearing edge, sides above the sportsbook's fair price, Brier score, markets on disk |
| Non-sports scan | `scan --json` | Every modeled side (sortable, searchable, filtered to "clears costs" by default), the economic releases, the short-dated list, and the run's notes and caveats |
| Sportsbook comparison | `compare --json` | Each priced side with break-even, fair, alt fair, edge, EV, and ROI. The capture gap, with a STALE banner when it is past the limit |
| Calibration | `calibrate --json` | A reliability diagram (price against realized YES rate, with Wilson 95% intervals) next to the bucket table |
| Data on disk | `--db` | Per series: markets, open, settled, snapshot runs, last snapshot and its age, fee schedule. Sportsbook captures per sport |

Two warnings are generated by the dashboard itself:

* **Large edges.** When clearing sides show an edge over 10 probability points, the scan section says how many and says why that is suspicious. A model that disagrees with a traded book by that much is usually missing something. The weather model's forecast error is an assumption that has not been fit to settlements, so those edges are a list of disagreements to check, not money on the table. The threshold is `LARGE_EDGE` in `kalshi_edge/dashboard_render.py`.
* **An old file.** The page is a snapshot. When it is opened more than `--stale-hours` after it was built, a banner says so.

## Flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `--scan PATH` | none | Report from `scan --json` |
| `--compare PATH` | none | Report from `compare --json`. Repeatable |
| `--calibration PATH` | none | Report from `calibrate --json`. Repeatable |
| `--db PATH` | none | SQLite file to summarize. Opened read-only |
| `--out PATH` | `dashboard.html` | Where to write the page |
| `--stale-hours N` | 26 | Age past which the scan, comparison, and snapshots are flagged stale. 26 is a daily run plus slack |
| `--calibration-stale-days N` | 8 | Same for calibration, which is a weekly run |
| `--tz NAME` | `America/Chicago` | Time zone for displayed times |
| `--title TEXT` | `Kalshi Edge Finder` | Page title |

Exit codes match the other commands: 0 on success, 2 for a bad argument or an input that cannot be used, 1 if the output file cannot be written. On any failure the previous `dashboard.html` is left as it was.

## Why it is built this way

**A file, not a server.** The data changes when a batch command runs, a few times a day. A page rebuilt after each run shows everything a live server would. A server would add a listening port, a login to get right, and software to keep patched, in exchange for nothing this project needs. A file can be opened from disk or sent as an attachment.

**No network, and the browser enforces it.** The stylesheet and the script are inside the file. The page carries a Content-Security-Policy that allows exactly those two blocks, each by its SHA-256 hash, and nothing else: no CDN, no fonts, no images from a URL, no inline `style=""` attributes, no inline event handlers. The practical effect is that a script that is not ours cannot run in this page, even if one somehow got into it.

**Everything from a report is escaped.** Market titles, tickers, team names, and notes come from other people's APIs. Each one goes through one escaping function before it reaches the page, so a title containing `<script>` is displayed as text. Numbers are parsed to floats and formatted here, so a string in a numeric field cannot carry markup either. `tests/test_dashboard.py` has a sweep that replaces every string in every report and in the database with an attack string and checks that none of it reaches the page raw. A new field is covered by that test without anyone having to remember.

**The database is opened read-only.** `MarketStore` runs migrations and writes the schema version when it opens a file. A viewer should not change what it is looking at, so the dashboard uses SQLite's `mode=ro` instead. It cannot create a missing file, cannot migrate, and cannot hold a write lock while a collector is running. Only the file's name is printed on the page, not its full path, because the page gets sent around and a path gives away a home directory.

**It never recomputes an edge.** Break-evens, fees, and model probabilities are read from the report that calculated them. A second copy of that math here would be a second place for a bug, and the two copies would drift.

**The page works with scripts off.** Every table and chart is complete HTML when the file is written. The script adds sorting, filtering, tooltips, and the old-file banner. A chat app's file preview that does not run scripts still shows everything.

**The write is atomic.** The page is written to a temporary file in the same directory and renamed over the target. Whoever opens `dashboard.html`, including a bot about to send it, gets the old page or the new one and never half of one.

## A daily routine

```bash
#!/usr/bin/env bash
# Stop at the first failure. Without this, a failed scan would be followed
# by a dashboard built from yesterday's scan.json.
set -euo pipefail

python -m kalshi_edge.collect --config config/series.example.json --mode snapshot
python -m kalshi_edge.scan --json scan.json
python -m kalshi_edge.dashboard --scan scan.json --db data/kalshi.db --out dashboard.html
```

Add `--compare` after an `odds` and `compare` run, and `--calibration` after the weekly `calibrate` run. Leaving last week's `calibration.json` in place is fine. Its chip turns to Stale after eight days.

## What it does not do

* It does not fetch anything. If the reports are old, the page is old, and says so.
* It does not keep history. Each build replaces the file. Trends over time would need the snapshot history in `price_snapshots`, which is on the roadmap as its own piece of work.
* It is not a monitoring system. Whether the collector ran, how long it took, and how many Odds API credits are left are metrics about a running pipeline. That is what Prometheus and Grafana are for, and it is a separate project from this page.
